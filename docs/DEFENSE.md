# Финал: 4 личных репозитория и защита

**Запреты в названии репо:** название команды, ФИО, слова «Авито» и «хакатон». Запрет касается названия (и на всякий случай — описания) репозитория, не содержимого кода.

## Принцип деления

Деление повторяет реальные зоны из README — на защите каждый говорит о том, что писал. Каждая часть закрывает свои критерии жюри, вместе — все девять. У каждого в части есть и код, и продуктовая история: жюри прямо пишет «сильное решение — это не столько код, сколько продуктовая логика».

**Формат личного репо (одинаковый для всех):** полная копия проекта одним коммитом (проект обязан подниматься через `docker compose` из любого репо — это критерий), поверх — личный README: общий README переехал в `docs/PROJECT.md`, а корневой описывает лично твою зону. Так любой репозиторий самодостаточен, а вклад читается с первого экрана.

**Шаблон личного README:** одно предложение о проекте и ссылка на прод → «Моя зона» (таблица: директория → что в ней) → 3–4 ключевых решения с обоснованием → как запустить → метрики зоны (тесты, строки, эндпоинты) → что защищаю на презентации.

## 1. Владимир Антыгин — «Экономика и прогрессия питомца»

**Репо:** `virtual-pet-economy` (варианты: `pet-progression-engine`, `companion-economy-core`).

**Зона кода:** `src/backend/internal/module/pet/domain` целиком + доменные тесты: параметры и ленивая деградация, стадии и состояния, экономика XP и уровни, серии с заморозками, каталог наград, HMAC-подпись промокодов, квесты, лидерборд-правила.

**Текст для организаторов (пункт 2):**
> Защищаю игровое ядро проекта: доменную модель питомца и экономику прогрессии. Параметры питомца и их ленивая деградация без фоновых задач; формула опыта, уровни и стадии; серии ежедневных заходов с заморозками; ежедневные квесты с детерминированной ротацией; каталог наград и безопасная выдача персональных промокодов (HMAC-подпись, одноразовость, привязка к пользователю); правила лидерборда. Покрытие доменной логики юнит-тестами.

**Скелет выступления (2 мин):** экономика отвечает на главный вопрос кейса — «почему пользователь вернётся завтра»: чек-ин даёт быстрый XP и держит серию → серия даёт множитель → квесты дают среднесрочную цель → награды конвертируют уровень в действия на доске. Деградация параметров ленивая — считается при чтении, ноль фоновых задач. Промокоды: главное правило кейса «награда привязана к пользователю» — подпись HMAC, активация одноразовая, повтор — 409.

**Вероятные вопросы жюри:**
- Почему такие коэффициенты XP и потолки? → суточные потолки против фарма, дедупликация действий в журнале `xp_events`, циферки калиброваны от «7 минут в день — виден прогресс».
- Как награду не используют двое? → код выдаётся конкретному пользователю, подписан, активация идемпотентна.
- Что мешает накрутить просмотры? → дедуп по (пользователь, действие, объект) + суточные лимиты.

## 2. Калинин Артём — «Событийная шина и реалтайм»

**Репо:** `realtime-events-backbone` (варианты: `event-driven-pet-state`, `hot-state-pipeline`).

**Зона кода:** `src/backend/internal/module/pet/app` (подписчики, идемпотентный консьюмер), `src/backend/internal/module/pet/infra` (Redis hot-state, Lua, пакетный сброс в PostgreSQL, дедупликация), `src/backend/internal/module/pet/api` (WebSocket-хаб) + событийная шина с доставкой после коммита.

**Текст для организаторов (пункт 2):**
> Защищаю интеграционный слой и реальное время: событийную шину, связывающую модули маркетплейса и питомца без прямых зависимостей, с доставкой событий только после коммита транзакции; идемпотентную обработку и дедупликацию событий; горячее состояние питомца в Redis с атомарными Lua-скриптами и пакетным сбросом в PostgreSQL; WebSocket-хаб — состояние питомца, опыт и награды прилетают клиенту в реальном времени, как требует кейс.

**Скелет выступления (2 мин):** маркетплейс не знает о питомце — публикует события; питомец подписан. Доставка после коммита — нет призрачного XP за откаченные транзакции. Горячие параметры — в Redis (атомарность через Lua), периодический сброс в PostgreSQL — БД не грузится на каждый клик. WS — единственный источник правды для UI: покормил в одной вкладке — увидел в обеих.

**Вероятные вопросы жюри:**
- Не оверкилл ли для MVP? → шина упрощает: модули развиваются независимо, событие — контракт; идемпотентность делает ретраи безопасными.
- Что при падении Redis? → состояние восстанавливается из PostgreSQL, Redis — кэш горячего, не источник истины.
- Как переживается обрыв WS? → клиент переподключается и рефетчит состояние, событийная лента не критична к потере.

## 3. Никита Денисов — «Фронтенд и живой персонаж»

**Репо:** `raccoon-companion-ui` (варианты: `living-pet-frontend`, `companion-web-app`).

**Зона кода:** `src/frontend` целиком: дизайн-система и токены, экраны питомца/наград/лидерборда/объявлений, Lottie-персонаж и микровзаимодействия, WS-клиент с переподключением, TanStack Query + zod, i18n ru/en, темы, тесты Vitest.

**Текст для организаторов (пункт 2):**
> Защищаю клиентскую часть: дизайн-систему в стилистике бренда с тёмной и светлой темами; живого Lottie-персонажа с микровзаимодействиями (глаза следят за курсором, реакция на поглаживание, эмоции от событий); экраны питомца, наград, достижений, лидерборда и объявлений; WebSocket-клиент с автопереподключением и синхронизацией с TanStack Query; валидацию ответов API через zod; локализацию ru/en без хардкода; компонентные тесты Vitest.

**Скелет выступления (2 мин):** питомец должен ощущаться живым — иначе тамагочи мёртв: глаза за курсором, поглаживание кликом, речевые реплики по состоянию, всё в реальном времени через WS. Дизайн — узнаваемая палитра бренда, две темы, кастомные скроллбары, анимации переходов. Данные: TanStack Query как кэш, WS-события точечно обновляют кэш, zod ловит расхождения контракта на границе.

**Вероятные вопросы жюри:**
- Почему свои компоненты, а не Material UI? → дизайн-токены бренда + Base UI для доступной механики без чужого визуала.
- Как WS дружит с кэшем Query? → события пишут в кэш через `setQueryData`, при реконнекте — рефетч.
- Доступность? → фокус-ловушки модалок, aria на метриках питомца, клавиатурная навигация.

## 4. Михаил Хорохорин — «Маркетплейс, платформа и качество»

**Репо:** `marketplace-platform-core` (варианты: `secondhand-market-platform`, `listings-platform-infra`).

**Зона кода:** `src/backend/internal/module/{user,item,favorite}`, `raccoon`-фасад, загрузка и защищённая раздача фотографий, миграции goose и демо-данные, Docker Compose (dev+prod), nginx и HTTPS, линтеры, документация, деплой.

**Текст для организаторов (пункт 2):**
> Защищаю фундамент: модули пользователей, объявлений и избранного (жизненный цикл объявления от черновика до продажи, фотографии с безопасной загрузкой и раздачей); аутентификацию JWT и хранение паролей bcrypt; выбор и обоснование PostgreSQL, миграции и демо-данные; продакшен-контур — Docker Compose, nginx, HTTPS, метрики Prometheus; линтеры бэкенда и фронтенда; Trust & Safety: модерационный конвейер пользовательского контента. Отвечаю за продуктовую рамку: как действия на доске конвертируются в прогресс питомца и обратно.

**Скелет выступления (2 мин):** открыть с продуктовой петли (это первый критерий жюри): реальные действия на доске — публикация, улучшение, избранное — кормят питомца, награды возвращают в доску; замкнутый цикл, а не игра сбоку. Дальше платформа: модульный монолит со слоями api/app/domain/infra — скорость микросервисов не нужна, границы уже проведены событиями. PostgreSQL: транзакционность для экономики XP и наград критична, обоснование в README. Прод доступен по HTTPS, поднимается одной командой.

**Вероятные вопросы жюри:**
- Про инцидент с контентом → отвечаю я: внешний пользователь, снято сразу, теперь песочница видимости + ИИ-модерация fail-closed + rate limiting; описано в README, раздел Trust & Safety.
- Почему не микросервисы? → одна команда, один деплой; модули и события дают границы без сетевой сложности.
- Безопасность фото? → валидация типа и размера, раздача через контролируемый маршрут, файлы вне веб-корня.
