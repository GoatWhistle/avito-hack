# Кейс 1: «Авито Тамагочи» — полный разбор и план решения

> Рабочее название продукта: **«Авитыч»** — питомец, который живёт не в игре, а в твоём Авито.

---

## 1. Суть кейса

Авито хочет геймификацию «поверх» основного продукта: виртуальный питомец, за которым пользователь ухаживает, который растёт вместе с активностью пользователя и конвертирует заходы в игру в целевые действия на доске объявлений.

Ключевая фраза ТЗ: *«питомец должен давать реальную пользу клиентам Авито. Улучшение питомца — не самоцель, а путь к бонусам, которые можно применить в основном продукте»*.

### Обязательные требования (из ТЗ)

| # | Требование | Комментарий |
| --- | ----------- | ------------- |
| 1 | Пользовательский сценарий: регистрация → питомец → уход → опыт → уровни → награды | Ядро MVP |
| 2 | Документация: путь пользователя, параметры, прогрессия | Этот файл + README |
| 3 | Прогрессия и награды: экономика, понятный путь к бонусу, видимый прогресс | Раздел 5–6 |
| 4 | Награды привязаны к пользователю, защита от обхода и передачи | HMAC-подписанные одноразовые коды |
| 5 | Состояние питомца в реальном времени **через WebSockets** | Жёсткое требование по технологии |
| 6 | Лидерборд | Формат на наш выбор |
| 7 | Ежедневная сводка: что изменилось, прогресс, награды | Формат на наш выбор → делаем LLM-фичей |

### Требования по стеку

- **Frontend**: React 18+, TypeScript (у нас уже: Vite, AntD, Effector, React Query, react-router, zod, i18next — всё разрешено).
- **Backend**: Go; БД на выбор **с обоснованием**; Docker Compose; `.golangci.yaml` в корне (уже есть).
- **Оформление**: общий репозиторий, docker-compose, README.
- **ИИ**: использовать можно, но прозрачно (указать где и как); интеграция ИИ в MVP — плюс к оценке.

### Критерии жюри (0–5 за каждый)

1. Обязательная бизнес-логика — сценарий работает от начала до конца.
2. Доп. функционал — усиливает бизнес-задачу, не мешает MVP.
3. README — запуск без устных пояснений: запуск, зависимости, сценарии, API, ограничения, ключевые решения.
4. Тесты — юнит-тесты самых важных участков.
5. Линтеры — на беке и фронте, с правилами и обоснованием.
6. Дизайн и архитектура — понятный UI, разделение по зонам ответственности.
7. Продуктовые решения — обоснование, как достигается бизнес-цель.
8. Чистота кода — читаемость, без мёртвого кода, автопроверки качества.
9. Доступность в интернете — задеплоено, жюри проверяет по ссылке.

Вывод: **код — это только 3–4 пункта из 9**. Документация, продуктовая логика, деплой и качество процесса дают столько же баллов, сколько сама разработка. Планируем время соответственно.

## 2. Стратегия: как выиграть номинацию «Креативность»

Критерии номинации: необычный уместный сценарий, сильная продуктовая гипотеза, механика вовлечения, нестандартное использование AI, эффектная демонстрация, интеграция с логикой Авито, доп. функция, усиливающая MVP.

Риск кейса: его выберет половина команд, и у большинства будет «кликер с полосками голода». Выигрывает твист. Наш твист закрывает **все** критерии номинации одновременно:

### Главная продуктовая гипотеза

> **Питомец — это зеркало твоей активности на Авито, а не отдельная игра.**

Питомец не кормится кнопкой «покормить» в вакууме. Он живёт от реальных действий на доске объявлений:

- опубликовал объявление → питомец **поел**;
- зашёл сегодня → питомец **проснулся и рад**;
- заполнил объявление качественно (фото, описание, цена) → питомец **играет и растёт быстрее**;
- объявление продалось (перевод в archived как «продано») → питомец **празднует**, юзер получает крупный бонус;
- не заходил 2 дня → питомец **грустит** и присылает сводку «я скучаю»;
- объявление без фото → питомец грустит **и говорит почему** — это превращает игру в коуча по качеству объявлений.

Так геймификация напрямую конвертируется в целевые метрики Авито: публикации, качество контента, retention. Это и есть «решить бизнес-задачу, а не написать приложение».

### Стек твистов (по убыванию силы)

1. **Питомец-зеркало** (выше) — ядро, отличает нас от всех «кликеров».
2. **Питомец с характером через LLM** — обязательная «ежедневная сводка» реализуется не таблицей, а сообщением от питомца от первого лица: «Сегодня ты опубликовал 2 объявления, я наелся и вырос! Но у "iPhone 12" нет фото — с фото такие продаются в 2 раза быстрее, добавь, а?». AI генерирует текст **поверх детерминированных правил** — прогрессия остаётся воспроизводимой и честной, LLM только «озвучивает» факты. Обязательный пункт ТЗ превращается в запоминающуюся фичу.
3. **Вид питомца определяется тем, что ты продаёшь** — маппинг доминирующей категории объявлений на скин: электроника → робо-кот, детские вещи → плюшевый зверь, авто → механический пёс, по умолчанию — классический котик в палитре Авито. Дёшево (маппинг категория → SVG-скин), выглядит как персонализация.
4. **Безопасная экономика наград** — одноразовые промокоды, подписанные сервером (HMAC + user_id + nonce), активация только владельцем. Прямой ответ на пункт ТЗ «нельзя обойти» + отдельный слайд на защите.
5. **Streak с «заморозкой» как товаром** — пропустил день, серия сгорает, но питомец может заранее «найти на Авито» страховку за опыт. Механика удержания, обёрнутая в бренд.
6. **Демо-эффект** — item-модуль (уже готовый) работает как «мини-Авито»: на защите публикуем объявление, и питомец на глазах у жюри реагирует по WebSocket. Реалтайм-требование ТЗ становится вау-моментом демо.

### Почему пользователь вернётся завтра (ответ на главный вопрос ТЗ)

- **Незакрытый цикл**: вечером приходит сводка от питомца → повод открыть утром.
- **Страх потери**: streak и настроение питомца деградируют — терять жалко (loss aversion).
- **Видимый прогресс**: полоска XP, «до уровня 4 осталось 120 XP», «до промокода на доставку — 2 дня серии».
- **Переменная награда**: ежедневный «сюрприз-бокс» после первого действия дня (немного XP или редко — бустер).
- **Реальная польза**: награды применимы на Авито, а советы питомца реально улучшают объявления.

## 3. Пользовательский сценарий (user journey)

### День 0 — онбординг (цель: до первого «вау» < 60 секунд)

1. Регистрация (email + пароль — уже реализовано).
2. Сразу после регистрации пользователь получает **яйцо**. Экран: «Твой питомец вылупится после первого действия».
3. Подсказка-чеклист первых шагов: «Зайди — питомец проснётся», «Опубликуй первое объявление — питомец вылупится», «Дай питомцу имя».
4. Пользователь публикует объявление (мини-Авито внутри приложения, item-модуль) → **яйцо вылупляется в реальном времени по WebSocket** → +XP, конфетти, питомец здоровается по имени.

### День 1..N — ежедневный цикл (2–3 минуты в день)

1. Заход в приложение → **ежедневная сводка от питомца** (модалка): что было вчера, что изменилось, что заработано, 1 совет.
2. Ежедневный чек-ин засчитан автоматически → streak +1 → «сюрприз-бокс» за первое действие дня.
3. Главный экран: питомец, его настроение/сытость/энергия, полоса XP, «задания дня» (3 штуки, например: «ответь на сообщение», «добавь фото к объявлению без фото», «поиграй с питомцем»).
4. Действия пользователя на доске (публикация, обновление, продажа) автоматически кормят/радуют питомца — с реалтайм-реакцией.
5. Прямые игровые действия с лимитами: «погладить» (безлимит, немного настроения), «поиграть» (3 раза в день, +XP), «покормить лакомством» (если есть лакомства из наград).

### Прокачка и награды

1. XP копится → уровень растёт → на уровнях выдаются награды (промокоды, косметика, заморозки streak).
2. Экран «Награды»: все награды с условиями («Уровень 5», «Серия 7 дней», «Первая продажа») и прогрессом к каждой — пользователь всегда видит, что делать дальше (требование ТЗ).
3. Полученный промокод: персональный, одноразовый, с кодом активации и сроком годности.

### Сценарий оттока и возврата

- Пропуск 1 дня без заморозки → streak сгорает, питомец грустный, но не умирает (никакого жёсткого наказания — питомец не должен вызывать чувство вины, только лёгкую заботу).
- Пропуск 3+ дней → настроение и сытость на минимуме, питомец «спит»; первый же заход всё восстанавливает наполовину и даёт «бонус возвращения» — возвращаться не страшно.
- Питомец никогда не умирает и не убегает — это осознанное продуктовое решение: негативная мотивация убивает retention в утилитарных продуктах.

### Ключевые состояния системы (все предусмотрены — критерий жюри №1)

- Новый пользователь без питомца (только что зарегистрирован, до онбординга).
- Яйцо (питомец ещё не вылупился).
- Активный питомец: happy / neutral / sad / sleeping (по параметрам).
- Стадии роста: яйцо → малыш (lvl 1–4) → подросток (lvl 5–9) → взрослый (lvl 10–19) → легенда (lvl 20+).
- Streak: активен / заморожен / сгорел.
- Награда: доступна (условие выполнено) / получена / активирована / истекла.

## 4. Параметры питомца и действия

### Параметры (все 0–100, пересчёт ленивый — по timestamp, без крона)

| Параметр | Растёт от | Падает | Влияние |
| ---------- | ----------- | -------- | --------- |
| Сытость (satiety) | публикация объявления (+30), лакомство (+20), чек-ин (+10) | −2/час (до пола 0) | < 30 → питомец грустит, множитель XP ×0.5 |
| Настроение (mood) | «погладить» (+5), «поиграть» (+15), продажа (+40), быстрый ответ (+10) | −1.5/час | ≥ 70 → множитель XP ×1.25 |
| Энергия (energy) | восстанавливается со временем (+5/час) | «поиграть» (−20) | < 20 → «поиграть» недоступно, питомец спит |

Ленивый пересчёт: при каждом чтении состояния считаем `state(now) = clamp(state(last_update) + rate * hours_passed)`. Никаких фоновых джоб для деградации — проще, надёжнее, тестируемее.

### Действия и начисление XP

| Действие | XP | Лимит | Обоснование |
| ---------- | ---- | ------- | ------------- |
| Ежедневный чек-ин (первый заход дня) | 10 | 1/день | Ядро привычки |
| Публикация объявления | 50 | 3/день с XP | Целевое действие Авито №1 |
| «Качественное» объявление (фото + описание ≥ 200 символов + цена) | +25 сверху | — | Питомец-коуч повышает качество контента |
| Продажа (перевод в «продано») | 100 | — | Главная конверсия |
| Поиграть с питомцем | 15 | 3/день | Игровое вовлечение, но капы против гринда |
| Погладить | 0 (только настроение) | ∞ | Эмоциональная связь без абьюза экономики |
| Задание дня выполнено | 20 | 3/день | Направляет на целевые действия |
| Бонус за серию (streak milestone 3/7/14/30) | 30/70/150/300 | — | Награда за регулярность (требование ТЗ) |

Анти-абьюз: XP-начисления — только через append-only журнал `xp_events` с типом действия и дневными капами на сервере; удаление/пересоздание объявления не возвращает XP (кап по `item_id`); все правила — на бекенде, фронт ничего не начисляет.

### Уровни

Формула порога: `next_level_xp = 100 × level^1.5` (округление до 10). Итого примерно:

| Уровень | XP до следующего | Сумма | Реальный срок |
| --------- | ------------------ | ------- | --------------- |
| 1 → 2 | 100 | 100 | день 1 (онбординг гарантирует левел-ап в первый день) |
| 2 → 3 | 280 | 380 | ~день 3 |
| 3 → 4 | 520 | 900 | ~неделя |
| 5 → 6 | 1120 | ~2600 | ~2–3 недели |
| 10 → 11 | 3160 | ~10500 | ~2 месяца |

Принципы: первый левел-ап — в первый же день (быстрый дофамин), дальше кривая замедляется, но streak-бонусы дают регулярным пользователям ощутимое преимущество перед «набегами» раз в неделю.

## 5. Награды и экономика

### Каталог наград (MVP)

| Награда | Условие | Тип | Связь с Авито |
| --------- | --------- | ----- | --------------- |
| Бейдж «Вылупился» + имя питомца | Онбординг завершён | косметика | эмоциональная привязка |
| Промокод «Бесплатная доставка» | Уровень 3 | промокод | подталкивает к покупке с доставкой |
| Заморозка streak ×1 | Серия 3 дня | утилита | удержание |
| Скидка 10% на продвижение объявления | Уровень 5 | промокод | конверсия в платную услугу |
| Аксессуар питомцу (шарфик Авито) | Серия 7 дней | косметика | флекс в лидерборде |
| Промокод «Скидка на Автотеку» | Первая продажа | промокод | кросс-продукт |
| Эволюция скина (подросток) | Уровень 5 | косметика | видимый прогресс |
| Бустер XP ×2 на 24 часа | Серия 14 дней | утилита | ускоряет цикл в активные дни |
| Легендарный скин + рамка в лидерборде | Уровень 20 | косметика | долгосрочная цель |

Принципы экономики:

- **Три типа наград**: промокоды (реальная польза → конверсия на Авито), утилиты (заморозка, бустер → усиливают саму петлю), косметика (статус → лидерборд и привязанность). Смесь нужна, чтобы и «прагматики», и «коллекционеры» находили свою мотивацию.
- **Прозрачность прогресса** (требование ТЗ): каждая награда на экране «Награды» показывает условие и прогресс-бар к нему («Серия 7 дней — осталось 2»).
- **Промокоды в MVP — симуляция**: код генерируется и «активируется» внутри нашего приложения (меняет статус на activated). В реальном Авито активация дергала бы их промо-сервис; в README честно фиксируем это как ограничение MVP.

### Защита наград от обхода (обязательный пункт ТЗ)

Угрозы и ответы:

| Угроза | Защита |
| -------- | -------- |
| Передача кода другому человеку | Код привязан к `user_id`; активация — только авторизованным владельцем; сам код без аккаунта бесполезен |
| Подделка кода | Код = `base32(nonce)` + HMAC-SHA256 подпись `(user_id, reward_id, nonce)` серверным секретом; проверка подписи при активации |
| Повторная активация | Статус-машина `granted → activated → (expired)`; UPDATE со `WHERE status = 'granted'` — атомарно, гонки невозможны |
| Накрутка XP для получения наград | Дневные капы, append-only `xp_events`, идемпотентность по `(user_id, action, subject_id)`, все правила на сервере |
| Мультиаккаунты | Вне скоупа MVP (в проде: телефон/девайс-фингерпринт); фиксируем в README как известное ограничение |

Выдача идемпотентна: уникальный индекс `(user_id, reward_id)` — левел-ап при гонке двух запросов не выдаст награду дважды.

## 6. Реалтайм: WebSocket (жёсткое требование ТЗ)

### Архитектура

- Пакет `internal/shared/ws` (именно shared: depguard запрещает `net/http` в слоях app/domain модулей): **hub** — реестр подключений `map[userID][]*conn`, широковещание событий конкретному пользователю.
- Эндпоинт `GET /api/v1/ws` — апгрейд соединения; аутентификация по JWT: браузерный WebSocket не умеет заголовки → токен передаём query-параметром `?token=` (короткоживущий access) и валидируем тем же verifier'ом, что и HTTP.
- Библиотека: `nhooyr.io/websocket` (или `coder/websocket` — актуальный форк) — простая, контекстная, без глобального состояния, легче тестировать, чем gorilla.
- Один инстанс бекенда в MVP → hub в памяти процесса, без Redis pub/sub. Если инстансов станет больше — Redis; в docs фиксируем как осознанный трейд-офф.

### События (server → client)

```json
{ "type": "pet.updated",    "payload": { "satiety": 74, "mood": 91, "energy": 60, "state": "happy" } }
{ "type": "pet.hatched",    "payload": { "skin": "classic_cat" } }
{ "type": "xp.gained",      "payload": { "amount": 50, "reason": "item_published", "total": 380 } }
{ "type": "level.up",       "payload": { "level": 4, "unlocked_rewards": ["free_delivery"] } }
{ "type": "reward.granted", "payload": { "reward_id": "...", "title": "Бесплатная доставка" } }
{ "type": "streak.updated", "payload": { "days": 7, "milestone": true } }
{ "type": "pet.reaction",   "payload": { "emotion": "celebrate", "message": "Ура, продажа!" } }
```

Клиент шлёт только `ping`; все действия — через обычный REST (проще для тестов и отладки, WS — только канал уведомлений). Фронт: авто-reconnect с экспоненциальной задержкой, на reconnect — рефетч состояния через REST (single source of truth — REST, WS — оптимизация).

### Как события рождаются

Доменные хендлеры (публикация item, действие с питомцем, чек-ин) после успешного коммита транзакции публикуют событие в hub. Внутрипроцессная шина: маленький интерфейс `Notifier` c методом `Notify(userID, event)` — модуль item не знает о питомце, он просто эмитит `item.published`, а pet-модуль подписан и конвертирует в XP/сытость/WS-события. Это сохраняет модульность текущей архитектуры.

## 7. Лидерборд

- Метрика: **комбинированный рейтинг** = `level * 1000 + xp_in_level` (сортировка стабильная, простая, объяснимая) + отдельная вкладка «Серии» (по streak).
- Реализация: обычный SQL по индексу `(level DESC, xp DESC, user_id)` + keyset-пагинация. Текущий `shared/pagination.Cursor` жёстко завязан на `(created_at, id)` — для лидерборда нужен свой курсор `(level, xp, user_id)` (обобщить пакет или добавить второй тип курсора). До ~100k пользователей никакого Redis sorted set не нужно — фиксируем обоснование в docs.
- Позиция текущего пользователя: `COUNT(*) WHERE rating > my_rating` — одним запросом, показываем «Ты #47» со стрелкой изменения за день (снапшот вчерашней позиции — из daily summary).
- Продуктовая деталь: показываем соседей (±3 места) — «догони Ивана, ему до тебя 40 XP» — мотивация сильнее, чем топ-10 недосягаемых.
- Приватность: показываем имя пользователя и скин питомца, не email.

## 8. Ежедневная сводка + LLM-характер питомца

### Механика

- Таблица `daily_summaries`: генерируется на первый заход дня (лениво, без крона): агрегируем вчерашние `xp_events`, изменения питомца, награды, позицию в лидерборде.
- Показ: модалка при первом заходе + история сводок на отдельном экране («дневник питомца»).

### LLM-слой (главная AI-фича)

- Вход: детерминированные факты дня (JSON: события, XP, изменения параметров, проблемы объявлений — например «2 объявления без фото»).
- Промпт: «Ты — питомец по имени X с характером Y. Перескажи хозяину его день от первого лица, тепло, 2–4 предложения, дай ровно один конкретный совет по улучшению объявлений».
- Выход: текст сводки + (опционально) `advice_action` — кнопка «Исправить» ведёт прямо к объявлению без фото. **Совет = deeplink в целевое действие — это конверсия, а не украшение.**
- Модель: Anthropic API (claude-haiku-4-5 — дёшево и быстро) через минимальный собственный клиент; ключ в env.
- **Деградация без ключа/при ошибке**: шаблонная сводка из тех же фактов (текст собирается из заготовок). Демо не сломается, жюри без ключа тоже всё увидит. Прогрессия от LLM не зависит вообще — принципиально.
- Кэш: сводка генерируется один раз за день и сохраняется — повторные заходы читают из БД (расход токенов O(users/день), не O(заходов)).
- Второе применение LLM (если успеем): «питомец-коуч» — по запросу разбирает конкретное объявление и предлагает улучшенное описание.

### Прозрачность использования ИИ (требование ТЗ)

В README — раздел «Использование ИИ»: (а) в продукте — генерация сводок/советов поверх детерминированных правил, промпты в репозитории; (б) в разработке — Claude Code для генерации кода, документации и тестов, вся продуктовая логика и ревью — командные.

## 9. Технологии и обоснование БД

### БД: PostgreSQL (обоснование для docs/README)

1. Экономика наград и XP требует **ACID-транзакций**: начисление XP + левел-ап + выдача награды — атомарно; гонки решаются уникальными индексами и `SELECT ... FOR UPDATE`, а не приложением.
2. Модель данных реляционная насквозь: users → pets → xp_events → rewards → items; журнал `xp_events` — append-only таблица с агрегацией, это классический SQL.
3. Лидерборд и сводки — обычные индексированные запросы; на масштабе MVP (и даже 100k юзеров) Postgres справляется без специализированных хранилищ.
4. Один стор вместо зоопарка: Redis-контейнер сейчас поднят в docker-compose, но кода-клиента нет — он не используется вообще. Решение: **убрать redis из compose** (мёртвая инфраструктура — минус по критерию чистоты), в README описать, когда он понадобился бы (многоинстансный WS pub/sub, горячий лидерборд).
5. Уже в проекте: pgx, миграции goose, tx manager — нулевая стоимость входа.

## 10. Модель данных (PostgreSQL)

Существующие таблицы `users`, `items` не трогаем — только добавляем новые (миграции `00003+`, goose embed подхватит автоматически).

```sql
pets (
  id uuid PK,
  user_id uuid UNIQUE FK -> users,          -- один питомец на пользователя
  name text,
  skin text NOT NULL DEFAULT 'egg',         -- egg | classic_cat | robo_cat | plush | mech_dog | ...
  stage text NOT NULL DEFAULT 'egg',        -- egg | baby | teen | adult | legend
  level int NOT NULL DEFAULT 1,
  xp bigint NOT NULL DEFAULT 0,             -- суммарный XP (rating выводим из него)
  satiety int NOT NULL DEFAULT 70,          -- 0..100, значение на момент state_updated_at
  mood int NOT NULL DEFAULT 70,
  energy int NOT NULL DEFAULT 100,
  state_updated_at timestamptz NOT NULL,    -- точка отсчёта ленивого пересчёта
  hatched_at timestamptz NULL,
  created_at / updated_at timestamptz
)

xp_events (
  id uuid PK,
  user_id uuid FK,
  action text NOT NULL,                     -- checkin | item_published | item_quality | item_sold | play | task_done | streak_bonus
  subject_id uuid NULL,                     -- item_id для идемпотентности по объявлению
  amount int NOT NULL,
  created_at timestamptz NOT NULL,
  UNIQUE (user_id, action, subject_id)      -- где применимо: повторной выдачи за тот же item нет
)
-- дневные капы: SELECT count(*) ... WHERE created_at >= date_trunc('day', now() AT TIME ZONE user_tz)

streaks (
  user_id uuid PK FK,
  current_days int NOT NULL DEFAULT 0,
  best_days int NOT NULL DEFAULT 0,
  last_checkin_date date NULL,
  freezes int NOT NULL DEFAULT 0            -- запас заморозок
)

rewards (справочник, сидится миграцией)
(
  id text PK,                               -- 'free_delivery_lvl3'
  title text, description text,
  kind text,                                -- promo | utility | cosmetic
  condition_type text,                      -- level | streak | achievement
  condition_value int,
  payload jsonb                             -- скидка, скин и т.п.
)

user_rewards (
  id uuid PK,
  user_id uuid FK,
  reward_id text FK -> rewards,
  status text NOT NULL DEFAULT 'granted',   -- granted | activated | expired
  code text NULL,                           -- для промокодов: base32(nonce) + HMAC
  granted_at / activated_at / expires_at timestamptz,
  UNIQUE (user_id, reward_id)               -- идемпотентность выдачи
)

daily_summaries (
  id uuid PK,
  user_id uuid FK,
  date date NOT NULL,
  facts jsonb NOT NULL,                     -- детерминированные факты дня
  message text NOT NULL,                    -- текст от питомца (LLM или шаблон)
  advice jsonb NULL,                        -- { text, item_id } -> deeplink «Исправить»
  generated_by text NOT NULL,               -- llm | template
  UNIQUE (user_id, date)
)

daily_tasks (
  id uuid PK,
  user_id uuid FK,
  date date NOT NULL,
  task_type text NOT NULL,                  -- publish_item | add_photo | play_with_pet | ...
  status text NOT NULL DEFAULT 'pending',   -- pending | done
  UNIQUE (user_id, date, task_type)
)
```

Заметки:

- Часовой пояс: «день» считаем по МСК для всех (MVP-упрощение, фиксируем в README).
- `rating` не храним отдельно — `level` и `xp` уже дают сортировку; индекс `(level DESC, xp DESC, user_id)` на `pets`.
- Все переходы статусов — через `UPDATE ... WHERE status = ожидаемый` (та же дисциплина, что в item-модуле).

## 11a. Аватар питомца — центр всего продукта

Решение: питомец — не картинка в углу, а **живой персонаж уровня совы Duolingo**, на него выделяется отдельный человек в команде. Это главная ставка на номинацию «Креативность»: у всех будет прогресс-бар и спрайт, у нас — персонаж, с которым разговариваешь.

### Персонаж

- Имя-бренд: **Авитыч**. Форма — округлый зверёк в палитре Авито (синий #0af, зелёный, фирменные цвета как элементы: шарфик, пятнышко в форме логотипа).
- Скины по доминирующей категории продаж (эволюционируют, не выбираются): классический кот → робо-кот (электроника) / плюш (детские вещи) / механический пёс (авто).
- Стадии роста меняют силуэт: яйцо → малыш (большая голова, маленькое тело) → подросток → взрослый → легенда (аксессуары, свечение).

### Эмоциональная машина состояний

Слой 1 — фоновое состояние (из параметров, держится постоянно):

| Состояние | Условие | Поведение |
| ----------- | --------- | ----------- |
| idle/happy | параметры в норме | дыхание, моргание, случайные микродействия (потягивается, оглядывается) |
| hungry | satiety < 30 | смотрит грустно, живот урчит, показывает на кнопку «объявление» |
| sad | mood < 30 | уши вниз, вздыхает, изредка смотрит в камеру |
| sleeping | energy < 20 или ночь | клубок, zzz, мягкое сопение |

Слой 2 — реактивные эмоции (по WS-событиям, проигрываются поверх и возвращаются в фон):

| WS-событие | Анимация |
| ------------ | ---------- |
| pet.hatched | скорлупа трескается → вылупление → первый взгляд на пользователя (момент демо №1) |
| xp.gained (item_published) | ест, облизывается, довольный прыжок |
| level.up | фейерверк, кувырок, показывает новый уровень |
| item.sold | праздничный танец, конфетти, деньги-подушки |
| reward.granted | достаёт подарочную коробку, открывает |
| streak.updated (milestone) | огонёк серии разгорается, питомец греет лапы |

Слой 3 — микровзаимодействия (главный «эффект живости», очень дёшево и очень заметно):

- **глаза следят за курсором** (2 градуса свободы зрачков — самый сильный приём «он живой»);
- клик/тап по питомцу = погладить → жмурится, сердечки (та самая безлимитная кнопка настроения);
- долго не трогаешь страницу → питомец засыпает; вернулся на вкладку → просыпается и машет;
- наведение на полоску голода → питомец показывает на неё лапой.

### Связь с LLM-характером

Аватар и LLM-сводка — один персонаж: реплики сводки показываются в speech-bubble рядом с питомцем с его текущей эмоцией; советы («добавь фото») питомец «произносит» с указующим жестом. Характер в промпте фиксируется описанием: «слегка ворчливый, но преданный; радуется мелочам; говорит коротко».

### Технология

_(заполняется по результатам ресёрча — сравнение Rive / Lottie / SVG+CSS / спрайты / 3D, рекомендация и план Б)._

## 15. Демо-сценарий на защите (5 минут)

1. **Регистрация** нового аккаунта → на экране яйцо + чеклист. (30 сек)
2. **Публикуем объявление** в мини-Авито → на глазах у жюри по WS яйцо вылупляется, конфетти, +XP, левел-ап до 2. (60 сек)
3. Показываем **питомца**: параметры, действия, задания дня; публикуем объявление без фото → питомец реагирует и советует добавить фото. (60 сек)
4. **Награды**: прогресс к промокоду, активация кода на демо-аккаунте, показ HMAC-защиты (слайд «почему код нельзя передать»). (60 сек)
5. **Лидерборд** (заполнен сидами) + **сводка дня от питомца** (LLM-текст с советом и кнопкой «Исправить»). (60 сек)
6. Второй заранее прогретый аккаунт с demo-ускорением — показываем грустного голодного питомца и «бонус возвращения». (30 сек)

Запасной план: если LLM-ключ недоступен — шаблонные сводки (деградация встроена); если Wi-Fi жюри плохой — всё крутится локально в docker compose.

1. **Модуль `internal/module/pet`** по тому же шаблону слоёв (api/app/domain/infra) + `module.go New(Options)` + строка в `buildModules` (`cmd/api/main.go`) — вся логика питомца, XP, streak, наград, сводок. Один модуль, не четыре: домены сильно связаны транзакционно (XP → уровень → награда — одна транзакция).
2. **Внутрипроцессная шина событий** `internal/shared/events`: интерфейс `Publisher`/`Subscriber`, синхронная доставка после коммита. Item- и user-модули получают опциональный `Publisher` в Options и эмитят `item.published / item.sold / item.updated / user.registered`.
3. **WebSocket-хаб** `internal/shared/ws` (не в app/domain — depguard запрещает там `net/http`) + регистрация `GET /api/v1/ws`; аутентификация — существующий `auth.TokenService.Parse` по токену из query.
4. **LLM-клиент** `internal/shared/llm`: интерфейс `SummaryGenerator` с двумя реализациями (anthropic, template) — выбор по наличию ключа в конфиге.
5. **Конфиг**: `REWARD_HMAC_SECRET` (required), `ANTHROPIC_API_KEY` (optional), `LLM_MODEL`, `DEMO_TIME_FACTOR`; удалить мёртвый `REFRESH_TTL` (или реализовать refresh — решаем, скорее удалить).
6. **Миграции**: новые таблицы из раздела 10 + сид rewards + сид демо-пользователей.
7. **Курсор лидерборда**: свой keyset-курсор `(level, xp, user_id)` рядом с существующим в `shared/pagination`.

### Изменить

1. **item-модуль — статус-машина**: сейчас `draft → moderation → published → archived`, причём `publish` разрешён **только модератору/админу**. Для сценария кейса это блокер: обычный пользователь не сможет «опубликовать и покормить питомца». Решение MVP: разрешить владельцу прямой переход `draft → published` (модерацию оставить как опциональный путь и честно описать в README), плюс добавить терминальный переход `published → sold` — сигнал продажи для питомца (+100 XP, праздник).
2. **item-модуль — события**: эмит после коммита (published/sold/updated); проверка «качественного объявления» — чистая функция в pet-домене по данным из события (фото пока нет в модели item → критерий качества: описание ≥ 200 символов + цена + заполненные attributes; если успеем добавить фото-URL в attributes — учитываем и его).
3. **Онбординг**: `user.registered` → pet-модуль создаёт яйцо (сам user-модуль не знает о питомце).
4. **`server.NewRouter`**: WS-эндпоинт вне `chimw.Timeout` (общий таймаут убьёт долгоживущее соединение) — отдельная ветка роутера.
5. **nginx.conf фронта**: сейчас нет даже проксирования `/api` (фронт ходит на бекенд напрямую через CORS). Для WSS на проде добавить проксирование `/api` и `/api/v1/ws` с Upgrade/Connection и увеличенным `proxy_read_timeout` — иначе на HTTPS-домене будет mixed content.
6. **docker-compose**: убрать неиспользуемый redis-контейнер (см. раздел 9), добавить новые env.
7. **stack.yml (smoke CI)**: расширить сценарий — register → создать item → publish → проверить `GET /pet` (XP начислен).

### Удалить (мёртвый код — критерий чистоты)

### Ограничения, которые надо учитывать при разработке

- **Фронт**: `i18next/no-literal-string` + проверка синхронности локалей — каждая UI-строка требует ключа в `locales/ru/*` **и** `locales/en/*`; запрет хардкод-цветов (только токены `shared/design`); запрет TODO/FIXME в коде.

## 17. Распределение по команде (4 человека)

Состав: **Back A**, **Back B**, **Fullstack C**, **Frontend D**. Ключевое решение: **аватар — отдельная полноценная роль** (раздел 11a), это наша ставка на креативность, её нельзя делать «по остаточному принципу». Аватара берёт D (или тот, у кого лучше чувство визуала); C закрывает остальной фронт.

| Роль | Зона ответственности | Основные задачи |
| --- | --- | --- |
| **Back A — «Ядро питомца и экономика»** | модуль pet: домен | Параметры, ленивый пересчёт, состояния/стадии; XP-журнал, капы, формула уровней; чек-ин, streak, заморозки; каталог/выдача/HMAC/активация наград; юнит-тесты домена (самая тестируемая часть) |
| **Back B — «Интеграции, реалтайм, AI»** | шина + WS + item + LLM | Шина событий; правки item (публикация владельцем, sold, эмит); user.registered → яйцо; WS-хаб + auth + ветка без Timeout + nginx; LLM-клиент + шаблонный фолбэк; лидерборд; демо-ускорение; деплой |
| **Fullstack C — «Фронт приложения»** | все экраны кроме аватара | Страницы: награды, лидерборд, дневник, мини-Авито (доработка item-страниц), онбординг, модалка сводки; WS-клиент + Effector/React Query; ключи локалей; при простое — помогает A по бекенду (сводки, задания дня) |
| **Frontend D — «Аватар»** | персонаж целиком | Дизайн и сборка персонажа (скины × стадии × эмоции), эмоциональная state-machine, микровзаимодействия (глаза за курсором, тап-погладить), привязка к WS-событиям, speech-bubble для реплик LLM, страница питомца как сцена |

Общие зоны (владелец — но ревьюят все): README — C, деплой — B, презентация/демо — D + A.

Интерфейсные контракты фиксируем в первый день (разделы 6, 10, 11, 11a этого файла) — фронт мокает API по контракту и не ждёт бекенд; D первым делом фиксирует список эмоций и событий, дальше работает автономно в редакторе персонажа.
